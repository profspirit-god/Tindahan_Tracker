# AI Assistant Instructions — Tindahan Tracker

Read this before making changes if you're an AI assistant (Claude or otherwise) working on this codebase. It captures conventions and hard-won lessons from this project's actual development history — following them will save both developers real debugging time.

**Current version at time of writing: `v27.1.0`.** See "Versioning" under Process conventions below — the `MAJOR.CLEAN.MINOR` scheme is back in active use as of `v26.0.0`; read that note for the recent history before bumping a version.

## Project context

This is a single-file (`index.html`) web app for a real family-owned sari-sari store in the Philippines. End users are largely non-technical (a shopkeeper father, a co-owner mother, an aunt who works the counter) — the developer(s) are technical, but every UI decision should still assume the *user* is not. Keep interactions simple, forgiving, and bilingual (English + Filipino) where the app already does this.

**This is not a generic SaaS product.** Do not suggest build tooling, test frameworks, CI/CD, staging environments, or architectural patterns aimed at teams/scale unless explicitly asked. See `README.md`'s "Why so simple?" section — this has already been discussed and deliberately decided against.

## Architecture pattern — read this first

- **One giant `state` object**, mutated directly, then `saveState()` (writes to Supabase) followed by `render()` (rebuilds the visible DOM via `innerHTML`) — in that order, every time.
- **No virtual DOM, no diffing.** Every `render()` call fully rebuilds whatever's on screen from a `view` string (e.g. `view = "inventory"`) via a big if/else dispatcher inside `render()`. Current views: `home` (Store Health, default), `daily`, `gcash`, `payables`, `household`, `householdHistory`, `inventory`, `summary`, `help`, `insights`, `stockHistory`, `expansion`, `suppliers`.
- **Modals are shared, not per-feature.** There are exactly two reusable modal shells: `#chart-modal` (fullscreen chart expand) and `#item-modal-overlay` / `#item-modal-sheet` (bottom-sheet, reused for Add/Edit Item, Restock/Sold/Spoiled quantity entry, Supplier Price updates, and the Notification panel). **Reuse these rather than building new modal markup** for new features that need a popup/sheet.
- **The sidebar (`#sidebar`) is the only navigation.** There is no back button — it was deliberately removed. Every screen is reached via `go(viewName)` from the sidebar or a direct link elsewhere in the UI.
- **History/audit logs follow one pattern:** an array of `{..., by: currentUser, time: new Date().toISOString()}` records, append-only from the user's perspective but user-deletable with a confirm + (for Household History and Stock History) a separate passkey gate via `goHistoryProtected()` / `goStockHistoryProtected()`. If you add a new loggable action, follow this exact shape.
- **Read-only mode exists globally.** `isReadOnly` (toggled via `toggleReadOnly()`, a button on the Store Health screen) makes `saveState()` a no-op and blocks `importAllDataFromFile()`. Any new function that writes to `state` and calls `saveState()` doesn't need its own read-only check — `saveState()` already guards it — but any function that bypasses `saveState()` (there shouldn't be any) would need to check `isReadOnly` itself.
- **Destructive actions are undoable, not just confirmed.** There's a 30-second-expiring undo stack (`undoStack`, `pushUndo()`, `undoLast()`) covering row deletes, household-category deletes, history-entry deletes, and full-state resets. **When adding a new delete/reset action, call `pushUndo()` with the right `type` before mutating state** — don't just rely on `confirm()` alone; that's the established bar now, not confirm-only.
- **Data migrations that touch existing records should go through `runReversibleMigration(name, forwardFn, backwardFn)`**, which snapshots state first, applies the change, saves, and registers an undo entry — rolling back automatically if the forward function throws. Prefer this over a one-off inline loop when the migration is non-trivial or touches many records.
- **`payables` entries have a `type`** (`"One-time"`, `"Installment"`, or `"Consignment"`) and each type carries different fields — see the "Loan Management (Payables)" section below before touching this array. **Never read `.amt`/`.status` directly to figure out what's owed** — always call `getPayableBalance(p)`, which dispatches correctly per type. The same goes for due dates: use `getInstallmentNextDue(p)` / `getConsignmentNextDue(p)` rather than assuming a `.due` field exists (only One-time loans have one).
- **Consignment inventory tracking:** an Inventory item can hold both store-owned and consignment (unpaid, supplier-owned) stock at once, tracked via `item.consignmentStock` (a subset of `item.stock`, never a separate total). `getConsignmentPayableForItem(item.code)` finds the linked agreement, if any. **Sold/Spoiled always depletes consignment stock before owned stock** — this is a deliberate business rule baked into `applyStockDelta()`, not an implementation detail; don't "simplify" the depletion order without checking with the developer first, since it directly changes how much money the store owes.
- **Save-conflict detection:** `state._meta = {lastSavedAt, lastSavedBy}` rides inside the same jsonb blob (no separate Supabase column). `saveState()` compares the server's current `_meta.lastSavedAt` against the `lastKnownSavedAt` this device last saw, and warns via `confirm()` before overwriting if another device saved in between. This is optimistic-concurrency, not real merging — "Save Anyway" still overwrites the other device's change, it just makes that an informed choice instead of a silent one. There's a narrow (millisecond-scale) race between the check and the write that's accepted as a known, low-probability gap — don't "fix" it with a bigger sync rework unless it's actually caused a real problem.
- **The notification bell (`getNotifications()`) is the single place new alert types belong** — don't add a standalone banner elsewhere for something alert-shaped. It currently covers: Low Stock, Expiring Soon, Unpaid Loan (type-aware — see above), Price Alert, Supplier Today, and No Entry (missed/pending daily log, via `getLastDailyLogDate()`). When adding a new alert, follow the existing `{type, text}` shape and push into the same `notifs` array.

## Hard-won bug patterns — check for these before shipping

This project's real debugging history surfaced the same handful of mistakes repeatedly. Check for these specifically before telling a developer to push:

1. **A `<script src="...">` tag with inline code inside it.** The browser silently ignores all inline content when `src` is present — this caused a total app failure early on. Always use two separate `<script>` tags (one for CDN libraries, one for app code).
2. **Case-sensitive method typos** — e.g. `a.Click()` instead of `a.click()`. JS methods are case-sensitive; this exact bug happened.
3. **`removeChild` called on an element never `appendChild`'d.** If you write a download-trigger function, always include `href`, `download`, `appendChild`, `click()`, *then* `removeChild` — missing any one breaks the next. `downloadFile()` is the reference implementation; reuse it (as `exportAllData()` and `exportRows()` already do) rather than rewriting it.
4. **HTML entity typos** (`%nbsp;` instead of `&nbsp;`) — silently prints literal garbage text instead of failing loudly. Worth a visual double-check in generated documents/exports.
5. **A function called but never defined**, especially after a merge/edit (e.g. `getMonthSummary` and `syncStatus` both went missing this way at different points). If a `ReferenceError: X is not defined` shows up, grep the whole file for `X` first — it usually means a deletion happened somewhere unrelated to the current change, not a typo in the current one.
6. **Mismatched apostrophes in cross-sheet formula references** (this bit an Excel/xlsx deliverable once, not the web app — but the general lesson holds: escape special characters in any generated file, not just HTML).
7. **Dropdowns losing their selected value on re-render.** Because `render()` fully rebuilds the DOM from `state`, any `<select>` whose selection isn't tracked in a JS variable (not just read live from the DOM) will silently reset. Always track dropdown-driven UI state in a `let` variable and reflect it back with `selected` in the rendered HTML — see `rankMetric`/`rankOrder`/`hhRankOrder` (Insights) and `invCategoryFilter`/`invStorageFilter`/`invPageSize`/`invLowStockOnly`/`stockHistPageSize` (Inventory/Stock History) for the established pattern.
8. **Search/text inputs losing focus mid-typing.** Same root cause as #7 — every keystroke triggers a full re-render. Fix pattern: after re-render, re-`.focus()` the input and restore cursor position with `setSelectionRange()`. See `setInvSearch()` for the reference implementation.
9. **Restock/Sold/Spoiled routing is no longer "composite = modal, simple = `prompt()`".** That was true through `v26.x`. As of `v27.0.0`, `openQtyModal()` also handles simple (non-composite) items, and `restockItem()` routes a simple item through the modal too whenever it's linked to an active Consignment payable (it needs the extra Owned/Consignment source picker, which a native `prompt()` can't show). `sellItem()`/`spoilItem()` still use `prompt()` for simple items regardless of consignment linkage, since depletion there is automatic with no extra choice to make. If you're touching any of `openQtyModal`, `submitQtyModal`, `restockItem`, `sellItem`, or `spoilItem`, re-check which path a given item actually takes before assuming — don't assume "simple item" means "prompt() path" anymore.

## Loan Management (Payables) — data shapes by type

Every entry in `state.payables` has a `type`. Existing entries without one default to `"One-time"` via `ensureInventoryFields()`.

| | `"One-time"` | `"Installment"` | `"Consignment"` |
|---|---|---|---|
| Fields | `amt`, `due`, `status` (`"Unpaid"`/`"Paid"`) | `totalAmt`, `frequency` (`daily`/`weekly`/`monthly`/`annual`), `startDate`, `periods` (optional), `history[]` | `linkedItemIds[]` (Inventory `.code` values), `chargeForSpoilage` (bool), `history[]` |
| Balance | `getPayableBalance(p)` → `p.status==="Paid" ? 0 : p.amt` | `getPayableBalance(p)` → `totalAmt − getInstallmentPaid(p)` | `getPayableBalance(p)` → `getConsignmentBalance(p)` (accruals − remittances) |
| `history[]` entries | n/a | `{date, amount, by, kind:'remittance'}` — manual only | `{date, amount, by, kind}` where `kind` is `'sale-accrual'` / `'spoilage-accrual'` (both auto-logged from `applyStockDelta()`) or `'remittance'` (manual, via the shared payment modal) |
| Next due | `p.due` directly | `getInstallmentNextDue(p)` — pure calendar math off `startDate + frequency`, independent of payment progress | `getConsignmentNextDue(p)` — looks up the linked supplier (`state.suppliers.find(s=>s.name===p.name)`) and only resolves a date for `scheduleType==="Fixed Day"`; returns `null` for Irregular/Canvass-Only (handled as an always-on notification instead) |
| Logging a payment | `markPaid(idx)` — binary | `openLoanPaymentModal(idx)` → `submitLoanPayment(idx)`, shared with Consignment | same shared modal, labeled "Log Remittance" instead of "Log Payment" when `type==="Consignment"` |

**Known limitations, not yet built (ask the developer before adding):** no editing an existing loan's fields once created (delete + recreate only); if two Consignment payables somehow link the same Inventory item, `getConsignmentPayableForItem()` just returns the first match found.

## Style conventions

- **Colors/fonts:** CSS custom properties at the top of `<style>` (`--cover`, `--brass`, `--teal`, `--bad`, `--good`, etc.) — a "ledger book" aesthetic (navy/cream/brass), intentionally chosen to feel familiar to users coming from a physical notebook. Reuse these tokens; don't introduce new one-off colors.
- **Confirm before destructive actions, and register an undo entry.** Every delete button, every category removal, every value that could zero out a real number goes through `confirm()` first, *and* pushes an undo action via `pushUndo()` (see Architecture pattern above). This was explicitly requested after an accidental data loss — do not skip either half for new destructive actions.
- **Bilingual labels** on user-facing text where the app already does this (English primary, Filipino as a subtitle or alongside) — match the existing tone, don't translate everything, focus on the phrases a non-technical Filipino parent needs to understand at a glance. The `help` view (`renderHelp()`) is the fullest example of this and is a good reference for tone/phrasing when writing new user-facing copy.
- **Money is always formatted via the shared `peso()` helper** — never hand-roll a `₱` string for a dynamic value. (Static labels like `Amount (₱)` next to an input are fine as literal text — that's not the case this rule guards against.)
- **Never mix the four "money pots"** (Store Cash / GCash Float / Household / Expansion) in a calculation. If a new feature needs to reference money, be explicit about which pot it belongs to and don't let it leak into another pot's totals (e.g. Store Health's Revenue/Expenses must never include Expansion or GCash float movements — verify against `getMonthSummary()` as the reference implementation of correct pot isolation).

## Process conventions

- **Versioning:** the documented policy is `vMAJOR.CLEAN.MINOR` (MAJOR = new tabs/structural/data-model changes, CLEAN = bug fixes/cleanup, MINOR = small tweaks — see README). **`APP_VERSION` was a single incrementing integer through `v25.0.0`, but the three-part scheme has been in active use since** — recent history: `v26.0.0` (Installment loan type — MAJOR: new data model), `v26.1.0` (save-conflict detection — CLEAN: bug fix), `v27.0.0` (Consignment loan type + Inventory linkage — MAJOR: new data model, cross-feature), `v27.1.0` (missed-daily-entry reminder — MINOR: additive, no new fields). Current version: **`v27.1.0`**. Always check the actual `APP_VERSION` constant before citing "the current version" to the developer — don't rely on this document's number without verifying, since it can drift out of date the same way it did before. When delivering a change, always state which digit you're bumping and why (MAJOR/CLEAN/MINOR) and give the exact new version string and commit message together — don't make the developer ask.
- **Give exact paste locations.** This codebase has been built entirely through an AI assistant giving code snippets with precise "find this / replace with this" instructions, not full-file rewrites. Keep doing this — it's faster to verify and less error-prone for a non-full-time developer to apply.
- **Test order for any change:** apply locally → push → hard-refresh the live GitHub Pages URL (browser cache regularly causes false "it's not working" reports) → check browser console for errors → confirm existing real data isn't broken, not just a fresh test account.
- **Don't speculatively add features or defensive code for problems that haven't happened.** This project's entire development pattern has been: real friction/bug reported → fixed. Resist the pull to gold-plate; if you notice something *might* be worth fixing, mention it and let the developer decide, don't just add it. (Note: the undo stack, read-only mode, and `runReversibleMigration()` already exist in the codebase and are now part of the established pattern — reuse them; this rule is about *not adding more* beyond what's there, not about removing what's already shipped.)
